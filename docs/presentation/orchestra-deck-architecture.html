Challenge 1 — Multi-Agent Task Solver

The brief, and the shape of the answer

Accept a high-level business request in plain language — e.g. “Summarize the last 3 quarters’ financial trends and create a chart” — then use multiple specialized AI agents to break down the task, execute subtasks, and return a final structured result.

Solo. 24 hours.

Core requirements — all five

#RequiredShipped asStatus
1Plain-text business request A single command taking the request as its argument ✓
2Planning — which agents, and what each does One orchestrator call returns a validated dependency graph. Plan shape follows the request ✓
3Execution — agents work and share results Three specialist roles, real tools, dependency-driven concurrency ✓
4Aggregation into a final answer Synthesis pass → executive summary, sourced figures, chart ✓
5Visibility — progress per agent Live dashboard on the diagnostic stream, driven by an event bus ✓

Stretch goals

Multi-turn refinement after output ✗ Timeboxed and cut. Filed, not forgotten

Expectations

Bottom line

All five core requirements, every expectation including the high-marks one, and one of two stretch goals. 653 tests, offline, driving the whole application end to end.

The rest of this deck is about the four architectural decisions that made that possible in a day, and the three places they run out.

Architecture

Four decisions, and what each one bought

Nothing here is novel. The point is that each was chosen against a named alternative, and each one paid for itself inside the 24 hours.

DecisionAgainst the alternativeWhat it boughtWhat it cost
One-way dependency rule A conventional layered app where anything may import anything and discipline is a review comment The core is reusable behind any front end — or any language’s front end. And it is machine-enforced, so it cannot quietly rot Some indirection that a 24-hour prototype could technically skip
Ports and adapters Calling the vendor SDK directly from the agent code Adding a second model vendor is one new adapter and one line at the wiring point. The entire test suite runs against a fake implementation of one interface Today there is exactly one vendor and no runtime switch — the seam is proven by tests, not by a second implementation
One composition root Globals, singletons, or a service locator The whole system’s wiring reads in one screen, and substituting any part needs no patching framework Every dependency must be passed explicitly, which is more typing
Pointer ledger Passing results between agents directly Context cost scales with the number of steps, not the size of the data. Traceability falls out for free — a citation check becomes a set-membership test Invalidation is manual: re-running a step means walking the graph and clearing everything downstream by hand

Why this matters beyond this project

A policy layer that inspects context before it reaches a model is, in this architecture, a decorator on the model port — it wraps the vendor adapter, sees every outbound request, and can route, redact or refuse. And the interception surface is small precisely because specialists exchange pointers rather than payloads: there is one place where data becomes model-visible, not one per message between agents.

Execution model

One request, end to end

Two branches are worth watching: the clarification round happens before a plan exists, and the mid-run interrupt is honoured only when nothing is in flight.

Three properties, deliberately chosen

A failed subtask ends a step, not the run
Its dependents never become ready; everything independent of it still completes. Partial results beat no results, and the exit code carries the verdict so a caller need not parse text.
Two event delivery modes, not one
Progress may be dropped when a consumer is slow — blocking the agent loop to draw a frame is a bad trade. State transitions block with a timeout, because a dropped “step finished” strands the display on a spinner forever. Drops are counted either way.
Degrade, never lose
If synthesis fails, the run still reports what it produced — the artifacts are already paid for. Empty output would waste them.

The specialists

RoleDoesMay not
RetrievalFinds and loads raw dataAnalyse, or draw
AnalysisComputes over what an earlier step retrieved — by writing and running real codeFetch its own data, so a reported figure always traces to a step the plan ordered
VisualizationTurns computed figures into a chartFetch, or compute the figures it plots

Why analysis writes code rather than calling typed helpers

Analysis is open-ended. A fixed set of helpers answers only the questions enumerated in advance; everything else comes back “unsupported”. Running it in a separate short-lived process is what makes generated code affordable — a wall clock can kill it, and a runaway loop cannot take the orchestrator with it.

Stated precisely: that is isolation, not a sandbox. No network, no inherited secrets, a throwaway directory, a hard kill. It raises the cost of an accident. It does not contain an adversary — that needs a separate user, a container or micro-VM per call, and resource limits.

Designing for failure

A mechanism per named failure — not a promise

Every failure mode I could name got code and a default. The framing matters more than the list: failures are handled differently at each boundary, on purpose.

The mechanisms

Named failureMechanismDefault
Invented figureEvery reported figure must cite an artifact this run produced, or it is dropped from the report—
Malformed model outputValidate against a schema; feed the rejection and the rejected draft back, because a model cannot see its own previous message as data2 retries
Agent repeating itselfFingerprint each step by tool, input and output — the same call returning something new is progress — over a sliding windowwindow 10 / 5
Runaway agentPer-subtask ceiling on turns and on spend. A turn count alone will not catch an agent calling expensive tools6 turns / 60k

Two boundaries, two rules

At the tool boundary — failures are data

A bad argument, a missing file, a timeout, even a tool name that does not exist: all come back as readable content saying what was wrong and what would work. The model’s next turn is its own retry.

Throwing would unwind the agent loop and deny it that. Only a ceiling being hit is allowed to end the step.

At the process boundary — a typed taxonomy

Configuration problem, vendor problem, task failure, interrupted — each is its own class carrying its own exit code. A caller can distinguish “retry the provider” from “the task did not succeed” without reading a message.

Rendering happens once, at that boundary. Errors never format themselves.

“Why those numbers?”

Some are derived and some are judgement, and I can tell you which.

  • derived: output read ceiling
  • derived: preview size
  • derived: inline-vs-pointer threshold
  • judgement: 3 questions
  • judgement: 6 turns
  • judgement: 15 steps
  • judgement: 4 concurrent

The read ceiling is the character cap times the widest possible character encoding, plus one byte — so it can distinguish “hit the cap” from “reached the end just under it”. The preview size is backed out of the context budget. The judgement ones are reasoned but unmeasured — and what turns reasonable into right is the evaluation harness on the next slide.

One interaction I would fix

Repetition trips on the sixth identical call, and a subtask gets six turns. With one tool call per turn those two ceilings land in the same place — so the repetition guard only earns its keep when a single turn issues several calls at once. Either lower it, or state plainly that it is insurance against parallel calls.

Engineering discipline

The architecture is enforced, not documented

A convention nobody checks is a preference. The rules that a machine could check became commit gates, so the architecture fails at commit rather than at review.

Constraints, and what enforces them

ConstraintEnforced by
Dependencies point one way A lint configuration scoped to the inner core that bans upward and vendor imports outright. Violating the architecture is a failed commit, not a review comment
The core stays pure The same gate. This is what would let the engine sit behind a different front end — or a different language’s front end — unchanged
Output streams never mix A rule banning direct printing anywhere. Results and diagnostics each have one designated writer, so a redirect stays parseable
One of each thing A duplicate-detection gate, plus a written rule that a second parallel abstraction is a bug — if an interface does not fit, it changes for every implementer in one change
Types at every boundary A strict type checker, relaxed only at the vendor edge and scoped by path. Untyped SDK values are parsed into our own types immediately and never travel inward
Search before you write A written procedure, and every change states what it searched for and did not find. Not automatable — and it is the rule that actually prevents the mess

What that bought, concretely

Because one interface can be substituted at one place, 653 tests drive the real application end to end — the real command, the real orchestrator, the real scheduler, the real artifact store — with only the model replaced. No network, no patching framework, no mocking of internals.

The honest limit of that

Three different things get called “testing”. Two are covered.

QuestionCovered byStatus
Does it run?653 offline tests — plan shapes, retries, budgets, exit codes, cancellation, terminal restore ✓
Is it traceable?The citation guard — but it verifies the cited artifact exists, not that it contains the number ●
Is it right?Nothing ✗

The offline suite scripts a fake model to produce a known answer, then checks the plumbing carried it through. It cannot fail because a model reasoned badly — no model reasoned. Saying that plainly is more useful than a coverage number.

The harness I would build next

Correctness for an agent is a distribution, not an assertion. So it reports a pass rate across repeated runs with a numeric tolerance, gates only on the deterministic layers, and treats a model-as-judge as a report — never a gate.

Scale

Where it breaks first, and what replaces it

Every threshold below is derived from a constant in the repo, not measured. That is itself a finding.

The first thing that breaks is not the data volume — it is the catalogue, at thirteen files

The list of available datasets is capped and composed into two prompts: the retrieval tool’s description, and the planner’s roster of what the team can obtain. Past the cap it emits “…and 3 more not listed here”. The thirteenth file exists and would load fine, but its name appears in no prompt — and the unknown-name error is capped identically, so the model cannot discover it by failing either.

The roster closes with the clause that stops the model inventing data: nothing beyond those files and their own columns. At thirteen files that clause becomes actively wrong — it tells the planner that data we hold does not exist. The failure is not a stack trace. It is a well-worded refusal to answer a question we had the data for.

Fix: search the catalogue instead of reciting it — one more tool, one extra turn, and the anti-invention clause has to be re-derived from the search result rather than from a fixed list.

Then, in order

TriggerBreaksWhy
~3 large files in one subtaskThe spend ceilingTool output is re-sent whole every turn, so a large result is paid for repeatedly. The step fails and its work is lost
~20–40 data pointsThe chartDrawn from a bounded preview; past that the model fills the gap itself
Two runs in the same secondThe audit trailThe run directory is second-granular. Nothing is overwritten and the reports stay correct, but two runs’ artifacts mix
~8–10 subtasksThe work budgetIt counts every attempt including retries — and it is the one ceiling an operator cannot currently change
Hundreds of MBThe executor clockEach file is copied twice before the analysis reads it a third time
~10 concurrent runsThe hostOne process per run, no shared rate limit, no cost meter, no backpressure

Three axes, three different failure characters

AxisCharacter
More or bigger filesSilent and semantic. The catalogue break is a confident refusal, not an error. This is the axis that lies to you
More concurrent runsOperational and loud. No shared state to corrupt — because there is no shared state, which is also why there is no backpressure and no resume
Longer plansStructural. Step 9 has no idea what step 2 concluded unless the planner drew an edge. At three steps that is context hygiene; at twelve it is amnesia. And the graph is drawn in one call up front — there is no re-decomposition

What does not break: synthesis reads file heads, not files — a 10 GB artifact costs what a 1 kB one does. The parts designed to be bounded are bounded. Everything that breaks, breaks at a prompt boundary. That is where the scaling debt was put, on purpose.

What replaces it

Two things worth saying about that migration

The artifact store is the cheapest move in the repo — one interface with four methods, and previewing already reads only the head of a file, so it becomes a ranged fetch almost unchanged. Local disk to object storage is a backend swap, not a redesign. That is a concrete payoff of the pointer design.

The hard part is not the guardrails — it is leases. The work budget just needs to decrement in the same transaction that claims a subtask. But a worker that dies holding a claim needs a heartbeat, and the retry counter must then distinguish the worker died from the work failed. Today those are one counter; distributed, a flapping node would burn a run’s whole budget.

The point of view

Good for
A dozen or so datasets, files in kilobytes to megabytes, plans of three to ten steps, one operator, and a hard requirement that every number be traceable.
Would not use for
Answers that live in a warehouse. Untrusted input — the code executor is isolation, not a sandbox. Anything needing durable resume or run history.

Where I would deliberately not build yet

A general workflow engine — the graph is three to six nodes and the scheduler is small. A vector search layer — a catalogued directory is correct until the corpus stops fitting a catalogue. Agent-to-agent negotiation — it adds a failure mode before it adds a capability. A learned model router — static routing first; you need the evaluation harness before you can tell whether a router helped.

I add the abstraction when I have the second implementation, not the second idea. There is a receipt for that in the repo: streaming is specified in the model interface’s documentation and deliberately not declared — declaring it would force every adapter and every test double to implement dead code.

Glossary

Terms of art used in this deck, defined as they are used here specifically.

Architecture

port
An interface declared by the inner core stating what it needs — a model, a tool, a way to ask the user a question. It names the capability, never the technology.
adapter
An outer-layer implementation of a port: the vendor client, the terminal, the test double. Vendor types stop here and never travel inward.
composition
root
The single place that constructs every service and hands each one its dependencies. Nothing below it builds anything, which is what removes the need for globals.
ledger
The one typed state object for a run: the plan, subtask statuses, artifact pointers, the event log, and the answers to any clarifying questions.
artifact
A payload written to storage by a step — a dataset, an analysis, a chart. Referred to everywhere by a pointer rather than by its contents.
pointer
A validated reference to an artifact. The unit that moves between steps, so shared state never carries a payload into a prompt.
slice
The narrowed view of the ledger a specialist receives: its own subtask and its declared inputs. Never the plan, the event log, or another agent’s artifacts.
roster
The list of data the team can actually obtain, composed into the orchestrator’s prompt so it plans only against sources that exist.

Execution

DAG
Directed acyclic graph. The plan: subtasks as nodes, dependencies as edges, no cycles — so a valid execution order always exists. A cycle the model invents is rejected when the plan is constructed.
completion-
driven
Re-checking which subtasks are ready on every completion, rather than running the graph level by level with a barrier between levels.
fan-out
Two or more steps with no dependency between them running at the same time.
back-
pressure
A slow consumer being able to slow its producer. Progress events deliberately have none — they are dropped instead, so drawing a frame can never stall the agent loop.
lease
A time-bounded claim on a unit of work, renewed by a heartbeat, so a dead worker’s task can be safely reclaimed. Needed by the distributed target, not by the current design.
replan
Replacing the unfinished part of a plan mid-run while keeping every completed step and its artifacts.

Correctness

provenance
Whether a stated number can be traced to the artifact that produced it. Distinct from correctness: a number can be correctly sourced and still answer the wrong question.
golden set
Hand-derived question and answer pairs over a fixed dataset, used to grade the system’s output rather than its plumbing.
model-as-
judge
A second model call grading free text against fixed criteria. Useful as a report, unreliable as a gate, because judges drift.
isolation vs
sandbox
Isolation raises the cost of an accident — no network, no inherited secrets, a throwaway directory, a hard kill. A sandbox contains an adversary, which needs a separate user, a container or micro-VM, and resource limits.
